# NearBuyGoods — Architecture & Mobile Foundation

## 1. Shape of the system

```
┌─────────────────────────── Clients ───────────────────────────┐
│  PWA (this repo: /public)   iOS app (Capacitor)   Android app  │
│  vanilla ES modules,        WebView = same PWA    WebView      │
│  offline shell (SW)         + native plugins      + plugins    │
└───────────────┬───────────────────┬───────────────────┬───────┘
                │  REST JSON + JWT (CORS-open for capacitor:// origins)
┌───────────────▼───────────────────▼───────────────────▼───────┐
│  API service  /api/v1  (server.js — zero-dep Node ≥18)        │
│  auth · catalog · discovery · recognize · commerce · business │
│  admin · events · notifications      OpenAPI: /api/openapi.json│
└───────────────┬───────────────────────────────────────────────┘
                │
┌───────────────▼───────────────┐   ┌───────────────────────────┐
│ Data store (MVP: JSON doc db  │   │ Future: Postgres+PostGIS, │
│ data/db.json, debounced write)│ → │ Redis, S3/CDN, queue,     │
│ geohash fields precomputed    │   │ vector index (CLIP/Qdrant)│
└───────────────────────────────┘   └───────────────────────────┘
```

Why this shape: the brief demands the web app *be* the web service for future mobile
builds. Every screen in the PWA talks to `/api/v1` over fetch — never to local data —
so a native shell pointing at the same base URL gets identical behaviour. The OpenAPI
document is the contract; generate Swift/Kotlin clients from it (`openapi-generator`)
if a fully-native UI is ever preferred over the WebView.

## 3. Mobile app build path (web → native)

1. **Wrap:** `npm i @capacitor/core @capacitor/cli && npx cap init NearBuyGoods app.nearbuygoods --web-dir=public`
   then `npx cap add ios && npx cap add android && npx cap sync`.
   The WebView loads the PWA from local assets; API base URL switches to production
   host via a config file (`public/env.js` generated at sync time).
2. **Native plugins at the web's weak points** (all already abstracted behind
   `js/recognize.js`, `store.js`, `alerts` page):
   | Capability | Web today | Native plugin |
   |---|---|---|
   | Camera / barcode | getUserMedia + BarcodeDetector | `@capacitor/camera`, ML Kit barcode |
   | Push | Web Notifications (foreground) + poll | `@capacitor/push-notifications` (FCM/APNs) |
   | Biometric login | WebAuthn | `@capacitor/biometrics` |
   | Background geofence | periodic sync | `@capacitor/geolocation` + native geofence plugin |
   | Haptics, splash, splash-safe areas | CSS env() | `@capacitor/haptics`, `@capacitor/splash-screen` |
3. **Deep links / universal links:** hash routes (`#/product/p1`) map 1:1 to
   `https://nearbuygoods.app/product/p1` paths server-side (already served via SPA
   fallback); configure AASA / assetlinks so shared links open the app.
4. **Offline:** service worker already precaches the shell and falls back to cached
   API GETs; in native, add SQLite outbox (`@capacitor/preferences` → later
   `@capacitor-community/sqlite`) to queue writes (reviews, reservations) and sync
   on reconnect — API is idempotent-safe via client-generated ids where needed.
5. **Store readiness:** privacy manifests (location, camera, notifications purpose
   strings), App Tracking Transparency prompt on iOS, signed Android build with
   Play App Signing, splash/icons generated by `tools/make-icons.js`.
6. **Release loop:** web deploys continuously; native shells ship WebView updates
   instantly (assets) and only re-submit for plugin/OS changes — optionally add
   CapGo/CodePush-style OTA for asset hotfixes.

## 4. API contract highlights

- Auth: `POST /auth/login|register` → `{token, user}`; `Authorization: Bearer <jwt>`.
- Discovery: `POST /search` (geo + filters + sort + paging), `POST /recognize`
  (signals → ranked candidates), `GET /products/:id` (offers + reviews + similar).
- Commerce: `POST /reservations` (stock hold), owner `POST /reservations/:id/status`.
- Business: inventory CRUD triggers watcher notifications server-side (price drop /
  back-in-stock), deals notify shoppers inside their saved radius.
- Events beacon: `POST /events` feeds store analytics (views/clicks/matches).
- Errors: `{error}` + proper status codes; 429 on auth brute-force buckets.
- Full machine-readable spec: `GET /api/openapi.json`, human docs: `GET /api/docs`.

## 5. Scaling & migration checkpoints

| Trigger | Move |
|---|---|
| >~50k offers or multi-city | JSON store → Postgres; spatial queries → PostGIS `ST_DWithin` (geohash column retained for shard routing) |
| Recognition latency >2 s p95 | Precompute catalog embeddings; cache per-image signals; move vision to queue + webhook |
| Feed/notification fan-out growth | Dispatcher service + Redis pub/sub; push via FCM topics per radius bucket |
| Multi-region NG + GH/KE launch | Currency & tax tables per jurisdiction; CDN edge caching of catalog reads |

## 6. Security model (as built)

scrypt password KDF · HMAC-SHA256 JWT (exp 30 d) · role guards (`store_owner`, `admin`) ·
per-IP token bucket on auth routes · CSP `default-src 'self'` + data/blob media ·
CORS `*` limited to `/api` (mobile shells & partner clients) with bearer auth carrying
identity · input validation on every write · GDPR export/delete in profile.
Production hardening list in RESEARCH.md §13.
